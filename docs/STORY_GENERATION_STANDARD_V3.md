# 三清问道：断语生成与审核规范 V3

用户最新原则：先规则，后结论，再自然语言表达。断语由本助手负责撰写；软件开发侧接入已写稿件，不把正式占断交给运行时模型自行决定。

## 判断顺序

1. 代码取得完整本卦、互卦、变卦、真实动爻和体用定位。
2. 具体问题选用相应门类占法；明确回答的是本轮催还、原条件成交等哪一个结果。
3. 完整读取动爻原文，优先审看爻意。保留吉、凶、贞吉、终吉、无咎、无不利等关键词及其条件。
4. 计算本用、体互、用互、变用对同一个原体的直接关系。
5. 对全部经卦使用同一套时令旺衰，包括有利方和不利方。
6. 结合领域、爻辞、本互变、旺衰处理冲突，形成有适用范围的结论。
7. 将已确定的结论写为自然中文，再审读简断与详断是否一致。

《占卜总决》mh-056明确“成卦之后先看《周易》爻辞”，其次体用生克；末段亦要求有凶有吉时详审，不能机械执取。优先读爻辞不等于把一个吉字换成固定加分，也不等于拿一个凶字自动覆盖所有变化。

## 三层数据

第一层为卦象事实，由 collectStoryFacts 调用原排盘代码与完整旺衰表计算。保存动爻全文、关键词位置、原文出处、六位置、四条直接关系和使用范围。inspectMovingLine 只保留词及上下文，不自动计算吉凶分数。

第二层为专业判断，保存 decisionId、outcomeCode、具体问题范围、爻意适用条件、相反证据、冲突采用口径和来源。现代应用与古籍原句明确区分，未形成规则的冲突保留 unresolved，不交给写作模型自行补解。

第三层为自然断语，包含标题、60–120汉字简断及开局、过程、结局、总断四段详断。两种文字绑定同一个 decisionId，由 getStoryCopy 同时取出。代码检查ID一致并不证明语义绝无矛盾，仍需逐篇实读。

## ④与⑦的冲突判例

当前仅登记两个精确项目判例，见 src/story-editorial.js 的 CONFLICT_CASE_POLICIES。它们是依据古籍与用户本轮审校采用的项目解释口径，不声称古籍直接给出了通用算法，不推广到其他季节、问题、爻位、空亡上下文。

④山雷颐初九、冬令晋升：艮土体囚，震木用相而克体；体互、用互、变用均为弱土比和，无直接生体。动爻全文有凶。承认后段比和改善了直接受制，但按mh-119“内外并无生体……皆是衰卦，终不吉”的条件，采用本轮晋升偏难成。mh-071在任见克条文可作谨慎参照，不移植为用户必遭处分或失业。

⑦水地比六二、冬令合同：坎水体旺，初用及两互的土均囚而克体；末后转为坎水得令比和。动爻“比之自内，贞吉”及小象“不自失也”保留守正的条件。承认前中段均有阻力，按mh-101、mh-119的旺体与衰克判断，结合末后得令比和，采用守住关键立场、条款谈清时后势改善、有望签成。

resolveConflictCase 严格匹配问题类型、卦号、爻位、月令、六位置旺衰、四条直接关系、完整动爻原文及分析范围。任何前提变化返回 unresolved。无自创分数，无语言模型选择权重；两例都不会因此自动取得九项正式发布批准。

## 用户可见文案

标题直接回答所问及主要倾向。开局写初期基础，过程写中间变化，结局把动爻与变卦共同连到末后判断，总断用自然中文回答问题并给出有针对性的实际建议。

禁止“不能把这些阻力写得过重”“不能叠加成更强压力”“不能单独当作找回结论”等内部审核语言。文案说明已经得出的解释，不教模型怎样判断。禁止虚构现实已经发生、确定谈判轮次、他人真实心理、未核算日期和古案反馈。

有依据的现实情节仅作可能的表现，例如“可能仍需反复商量”；不能把传统象意写成已核实事实。比和不等于已经签字，生体不等于款项已经到账。

失物页优先给实际操作。钱包先核查卡片、联系发卡行锁卡或核查交易、联系经过场所；手机先用系统查找、按支持情况启用丢失模式或远程锁定并保护账户。传统方位取象只作补充检索提示，保存 provesLocation:false，不提供虚假定位。
